# Tempest access, accounts, and templates

This is the implemented service access boundary, not a deployment migration.
The service hosts an administrator workspace at `/admin`, adapts the existing
live model interface at `/inference`, and serves the language index at
`/state-index`. The research personality editor, comparisons, audit tools,
paper corpus, and local research history have not been migrated into this service.

## Hosted Test model behavior

Play/Pause and Play random event use the same 42,565-event text pool as the local
live-mode corpus, packaged as `service/random_events.json`. Rebuild the pool with
`python service/export_event_pool.py SOURCE.sqlite service/random_events.json`.
`GET /admin/events/random` samples one text and is administrator-only. It neither
runs inference nor consumes an event turn. Labels and personality records are not
included in the packaged pool.

Playback sends ordinary event requests, targets a one-second cadence, and never
overlaps turns. Pause lets an in-flight turn finish and persist, then stops. Hidden
tabs pause; reload restores the selected instance without automatically playing.
Manual submission pauses playback. Random turns preserve a drafted manual event.
Failed event submissions keep their idempotency key for explicit retry.

Saved settings, state, pressure, relationship deltas, and history use the service,
not a second browser simulation. The existing seed/reset controls, effect-size and
per-state sliders, baseline markers, event-log inspection, history export, theme,
and tooltips are retained. Change labels show model category effect sizes before
recovery/multipliers; charts show the resulting current state. New turns include
a server timestamp. Earlier local research histories are not silently imported.

## First administrator and credentials

Set `TEMPEST_API_TOKEN` to a random secret of at least 24 characters before
starting `service/server.py`. Open `/admin`, enter that bootstrap secret, choose
a username, and set a password of 12–1024 characters. Setup creates the single
administrator and a browser session in the database. Setup can succeed only
once, including under concurrent requests.

`TEMPEST_API_TOKEN` is now a **setup-only credential**. Sending it as a Bearer
token does not authorize any API request, before or after setup. Existing API
clients using it must switch to an issued key. Existing personalities without
account ownership remain administrator-only; they are not automatically assigned
to a new API account.

Browser login uses the administrator username and password. The password is
stored as salted PBKDF2-SHA256 with 600,000 rounds. Sessions last 12 hours and use
an `HttpOnly`, `SameSite=Strict` cookie; production cookies are `Secure`. Session
tokens and API keys are stored as SHA-256 hashes. Login and setup failures are
persistently throttled, with five failures per 15-minute window; login also has
an administrator-wide bucket to limit source rotation.

Configure `TEMPEST_PUBLIC_ORIGIN` to the exact HTTPS origin of the workspace when
running behind a TLS proxy. Browser POST requests require JSON, the matching
Origin when present, and `X-CSRF-Token` from `/auth/me` for an authenticated
session. Protect the service with TLS before exposing it. The command-line
server does not provide a switch to weaken its secure production cookies.

Administrators issue separate Bearer keys through `/admin/keys`:

- An `admin` key grants administrator API access and is not bound to an account
  or user. It is a privileged automation credential; its scope labels do not
  reduce its administrator authority.
- An `account` key is bound to one API account and optionally one provisioned
  quota user. Its scopes are `text`, `create_description`, or both. The default
  account scope is `text`. Supplying a user at issuance provisions that user.

Raw keys are returned once on issuance. Listing returns metadata only. Save the
raw key securely; use the key ID to revoke it. The HTTP issuance endpoint accepts
`expires_days` from 1 to 3650 (default 90), or `-1` for no expiration. The UI
offers **Never expires (unlimited)**; these keys remain revocable and show
**Never** in the expiry column. This option affects newly issued keys only;
existing keys retain their tokens and expiration dates. Expired and revoked keys return 401.
Browser sessions, API keys, and the bootstrap secret are not interchangeable.

## Account ownership and response privacy

Administrators create API accounts and owned personality instances. Account IDs
are generated by the service; an optional unique `external_id` can link an
account to another system. The account-wide key can use all personalities owned
by that account. A user-bound key can use only personalities whose owner is that
same account and quota user. Cross-account and mismatched user requests return
404. Caller-supplied account/user fields do not override account-key identity.

Account API responses expose language plus IDs, names, and turns. They omit raw
baseline/current vectors, model categories, settings, pressure, configuration,
grant lists, and numeric relationship adjustments. `/schema`, configuration
editing, raw instance views, usage management, and template editing require an
administrator. Historical responses use the same language allowlist.

## Quotas and retries

The default daily limits are 1000 admitted event requests (`text`) and 10
description-generation requests (`create_description`) per API account. A batch
of 1–32 events is one request and one turn, not a charge per event. Reads and
template copies do not consume these quotas. Administrator work is unmetered.

Limits can be overridden at the default, account, and provisioned-user levels:

| Value | Meaning |
|---|---|
| `null` | Inherit from the parent; defaults fall back to the built-in values |
| `-1` | Unlimited at this level |
| `0` | Disabled |
| Positive integer | Daily request cap |

The account cap always applies. A bound user's effective limit adds a subcap
and cannot bypass the account cap, even when the user limit is unlimited. For
event processing, the personality's bound owner determines the user subcap;
an account-wide key cannot evade it. Counters use UTC calendar days. Editing a
limit does not erase usage.

Requests reserve quota atomically before work. Successful work retains the
charge; failed work releases it. Repeating the same identity, operation key,
and payload does not consume another quota unit. Concurrent failures cannot
refund a successful attempt. Interrupted work conservatively retains its
reservation; retry with the original payload and key. Reusing a key with changed
content returns 409. An exhausted quota returns 429. Description clarification
answers use a new key and consume one additional generation request.

## System templates and description creation

Every template is system-owned. Administrators choose its visibility:

- `system`: only administrators can discover or copy it.
- `restricted`: only administrators and explicitly granted API accounts can
  discover or copy it.
- `public`: every authenticated API account can discover or copy it.

Public does not mean anonymous. Account responses contain template language and
metadata; only administrators can inspect or edit baseline/settings and grants.
Copying creates a separate owned instance from a configuration snapshot. Later
template edits do not update that instance. Copy requests require an
`idempotency_key`. Completed retries return the original copy response even if
the source template or copied instance is later edited; changed request content
returns 409. Current template permission is checked again on every retry.

`POST /characters/describe` accepts either
`{description, idempotency_key}` or
`{draft_id, answers, idempotency_key}`. It may return `status: "questions"` and
1–10 clarification questions, or `status: "complete"`, a template, and a newly
owned instance. Account credentials create account-restricted templates and
instances. An administrator may omit `account_id` to create a system-only
template and an unaccounted system instance; supplying an account explicitly
keeps creation account-restricted. Drafts are isolated by account and bound
quota user; system-admin drafts use a separate internal namespace. Generated
output cannot choose ownership, visibility, grants, or credentials. There is
currently no HTTP endpoint for listing or fetching drafts independently of the
workflow.

No external creator is enabled by default. Without configuration the endpoint
returns 503 and sends no provider request. To opt in, configure both
`TEMPEST_CREATOR_URL` (an explicit OpenAI-compatible chat-completions URL) and
`TEMPEST_CREATOR_MODEL`, plus `TEMPEST_CREATOR_API_KEY` if the provider requires
one. HTTPS is required except loopback development. The provider receives the
character description, clarification answers, and the simulation schema/anchors.
Redirects are rejected. Configuration is an explicit operational choice; it can
incur provider cost and transmit description content. This change does not set
provider credentials or modify deployment configuration.

## Relationship event metadata

Both event routes accept plain strings and objects such as:

```json
{
  "events": [
    {"text": "A visitor thanks them for helping.", "user_id": "visitor-42"}
  ],
  "idempotency_key": "conversation-42-turn-7",
  "expected_turn": 0
}
```

Here `user_id` identifies the event actor or relationship target, not a quota
user, token principal, or authorization claim. It cannot move charges or grant
access. All events are classified against the same recovered global state and
combined into the normal global update **once**. Tagged events also accumulate
separate relationship adjustments per actor, using the same per-state effect
union and clamping the accumulated values to ±10. They do not create an extra
global turn and are not fed back into inference yet.

The accumulated relationship text uses a draft rendering policy: absolute
adjustment divided by 2.5, rounded to the nearest delta-index intensity and
clamped to 1–4 for any nonzero adjustment. Zero produces no change language.
This describes accumulated adjustment, not an inferred current global state.
The event response's relationship `delta_text` instead describes that turn's
model-category union. Administrator responses include numeric evidence;
account responses include only language, actor IDs, turns, and this policy.

## HTTP routes

Public routes are `GET /healthz`, `GET /auth/status`, the administrator shell
and its shared styles/theme assets, and `POST /auth/setup` / `POST /auth/login`.
The application APIs below require a valid session or issued Bearer key.

| Route | Methods and purpose |
|---|---|
| `/auth/me`, `/auth/logout` | GET session/CSRF details; POST logout (browser session only) |
| `/admin/accounts` | GET accounts; POST account with `name` and optional `external_id` |
| `/admin/keys` | GET metadata, optional `account_id`; POST issue key |
| `/admin/keys/{id}/revoke` | POST revoke |
| `/admin/limits` | GET overrides/inheritance; POST `text` / `create_description` limits, optional account/user |
| `/admin/usage` | GET today's UTC usage, optional account/user |
| `/admin/templates` | GET all templates; POST create |
| `/admin/templates/{id}` | GET raw configuration; POST edit |
| `/admin/instances` | GET instances, optional account/user; POST create with configuration and optional owner |
| `/admin/instances/{id}` | GET raw instance and owner; POST name/settings with required `expected_turn` |
| `/schema` | GET administrator schema |
| `/templates` | GET permitted templates (`text` scope) |
| `/templates/{id}/copy` | POST owned copy with `idempotency_key` (`text` scope) |
| `/characters/describe` | POST creation/clarification (`create_description` scope) |
| `/personalities` | GET owned instances (`text`); POST unowned registration (administrator) |
| `/personalities/{id}` | GET current state: full administrator view or account language |
| `/personalities/{id}/events` | POST event batch and idempotency key |
| `/personalities/{id}/events/users` | POST same event processing, with optional actor-tagged events |
| `/personalities/{id}/history?after=0` | GET up to 100 saved turns |
| `/personalities/{id}/status/users` | GET relationship records, optional `user_id` actor filter |
| `/personalities/{id}/users` | GET alias for relationship records |
| `/inference`, `/state-index` | GET administrator browser interfaces |
| `/api/state-index?kind=state` | GET administrator state/delta index; `kind=delta` selects delta |

An administrator supplies `account_id` and optional bound `user_id` when copying
or generating a character for an API account. Account keys derive both from
their authenticated principal. Configuration edits cannot change the original
baseline or ownership in this version.

## Verification and remaining scope

`python -m unittest discover -s service -p 'test_*.py' -v` exercises credential
storage, first-admin races, login throttling, expiry/revocation, isolation,
numeric response filtering, quotas and concurrent retries, template visibility,
description questions/validation, and relationship updates. Tests use a fake
classifier and injected generator with the real pressure and language engines;
they send no paid provider calls. PostgreSQL tests use random `tempest_test_*`
schemas and drop those schemas afterwards. A mounted-model smoke test and an
external creator integration test remain separate operational checks.

This implementation adds access/account/template administration and reuses the
hosted live/index views. It does not implement administrator password recovery,
multiple administrators, user login, ownership transfer, account deletion,
full research editor hosting, automatic event pools, or final relationship
feedback/calibration. Existing infrastructure has not been deployed or changed.
